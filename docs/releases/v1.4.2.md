# v1.4.2 (2026-10-31)

> **`osm-deploy verify` —— 让「部署能跑」和「部署正确」分开说。**
> 这是 v1.4.1 真机验证的直接产物：那一次我在 JEV-9B 上撞出 4 个错误，
> 而 25 个 mock 测试全过。**mock 只能证明逻辑自洽，证明不了答案对。**

## 问题

`deploy` 只保证「命令是按 model card 抄对的」，`ask` 只保证「能拿到返回」。
两者都回答不了一个最要紧的问题：**这个部署算出来的答案，对不对？**

用户按文档部署完、`curl` 拿到了 `{"true": 0.98}`，然后呢？他没有任何办法
知道这个 0.98 是「模型真的读懂了合同」，还是「tokenizer 坏了 / model 名填错
走了 System 2 / 校准时漏了 bias」。

## 三层自检

```bash
$ osm-deploy verify autotrust-jev-9b

【自检】autotrust-jev-9b   (autotrust/JEV-9B)
  形态     : service
  接口     : /v1/completions   model=jev-decision
  服务地址 : http://localhost:8000

  ✅ L0 配方  AutoTrust JEV-9B · service · /v1/completions · model=jev-decision
  ✅ L1 连通性  服务在线，'jev-decision' 已注册
  ✅ L2 结构    返回字段完整 · 1 请求 · 210 ms
  ✅ L3 答案    3/3 通过

  逐题：
    ✅ 自动续约条款识别
       预期 True 实际 True · p(true)=0.985
       （文本里明确写了「合同自动续期一年」）
    ✅ 违约金条款识别
       预期 True 实际 True · p(true)=0.996
       （文本里明确写了「20% 的违约金」）
    ✅ 否定项不应误判
       预期 False 实际 False · p(true)=0.031 · 取 1-p 得 0.969
       （文本里完全没有保密相关内容，正确答案是 false）

  ✅ 配方在这台机器上可用 —— 连通性、结构、答案正确性全部通过（3/3）。
```

| 层 | 查什么 | 典型失败原因 |
|---|---|---|
| **L0 配方** | 模型有配方、形态可检 | 模型没收录 |
| **L1 连通性** | `/v1/models` 可达 + `served_model` 已注册 | 服务没起、端口不对、model 名填错 |
| **L2 结构** | 请求能返回、字段形状对、分布 key 对 | 没带 `--logprobs-mode`、tokenizer 缺失 |
| **L3 答案** | 跑 golden set，比对正确答案与置信度 | 配方接口假设错、量化档位不同 |

## 三条设计原则

### 1. 没有 golden set 就明说「答案未验证」

12 个决策模型里，目前**只有 JEV-9B 有 golden set**（真机实测过）。

```bash
$ osm-deploy verify cloudflare-clef-flash-9b

  ✅ L1 连通性  服务在线，'Cloudflare/clef-flash' 已注册
  ✅ L2 结构    返回字段完整 · 1 请求 · 88 ms
  ➖ L3 答案    该模型没有 golden set（未真机实测过答案），只验证了连通性与结构

  ✅ 服务可用（连通性 + 结构通过）。
  ⚠️ 但 cloudflare-clef-flash-9b 的**答案正确性未验证** —— 它还没有 golden set。
     参考教训：JEV-9B 的配方在实测前有 4 处错误，mock 测试全过却完全不能用。
```

**不会**把「服务能跑」包装成「部署正确」。

### 2. library 形态报「不适用」，不算失败

```bash
$ osm-deploy verify convai-laya-multilingual

  ✅ L0 配方  Convai Laya 多语言版 0.3B · library
  ➖ L1 连通性  library 形态：进程内调用，没有 HTTP 服务，跳过
  ➖ L2 结构    library 形态：不适用
  ➖ L3 答案    library 形态：不适用

  ℹ️ 这是 library 形态（进程内 API，不是服务）。verify 只适用于有 HTTP 服务的模型
     —— 请直接用它的 Python API。这不是部署问题。
```

用户看到「❌ 这是 library 形态」会以为工具坏了；说清楚是设计就有用。

### 3. golden set 只收有客观答案的题

`src/core/golden_cases.py` 的收录原则写死在文件头：

- 只收**真机实测过**的，不抄 model card 的示例 —— 抄示例只证明「能返回」
- 每题必须有**客观答案**：合同里确实写了的条款。不收「风险等级=中」这种
- 记录实测概率作为 `prob_min` 参考，判分留余量（不同硬件有小幅漂移）

第三题「否定项不应误判」是**对照题** —— 防模型无脑答 `true`。没有这题，
前两题全对也可能是「什么都答 true」的坏模型。

## 🐛 顺手修的一个真 bug

写测试时抓到的：`noul` 的 `probability` 语义是 **p(true)**，
但 golden case 期望 `False` 时，我却拿 `p(true)=0.031` 去比阈值 `0.6` —— 
逻辑反了，答对的题被判成「置信度不足」。

```
❌ 修复前：否定项不应误判   预期 False 实际 False · p=0.031 · 低于阈值 0.6
✅ 修复后：否定项不应误判   预期 False 实际 False · p(true)=0.031 · 取 1-p 得 0.969
```

这个 bug 只有「期望答案是 False」的用例才能暴露 —— 而 golden set 里恰好有这一题。

## 🧪 测试守的是什么（11 个）

| 组 | 守的东西 |
|---|---|
| 失败路径 | 端口无人听 → L1 失败且不假装通过；未知模型/非决策模型报错 |
| 形态判断 | library → `applicable=False` 但 `ok=True`（设计不是失败） |
| 全通过 | 真 HTTP mock 服务 → L0/L1/L2/L3 全绿，且 `served_model` 被认出 |
| **答案错** | 服务正常、结构正常、**答案错** → `ok=False`（mock 测试永远抓不到的场景） |
| 结构坏 | 服务没带 `--logprobs-mode` → 拦在 L2，golden 不跑 |
| **诚实性** | 没 golden set → `ok=True` 但 conclusion **必须**出现「答案正确性未验证」 |
| 数据质量 | 每道 golden 题必须有 `why`（为什么这是客观答案）和 `expect_prob_min` |
| 渲染 | 四层标签 + 逐题明细都出现在输出里 |

## ⚠️ 边界

1. **只有 JEV-9B 有 golden set** —— 其余 11 个模型 `verify` 只做 L1/L2。
   要补 golden set，必须先真机跑一遍拿到实测概率（参考 v1.4.1 的做法）。
2. **golden 通过 ≠ 你的业务场景对** —— 它证明「模型能正确读这段文本里的条款」，
   不证明「在你行业的数据分布上校准良好」。阈值仍要在自己数据上验证。
3. **`ok=True` 的两种含义** —— 有 golden 时是「答案也对」；无 golden 时是
   「服务可用但答案未验证」。结论行会明确区分，读的时候看 conclusion 别只看 ok。
