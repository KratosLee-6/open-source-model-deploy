# v1.3.0 (2026-10-31)

> 一套参数打通 12 个决策模型 —— `osm-deploy ask` 把「单题接口 / 多题接口」「五个端口」
> 「三种部署形态」的差异全部吃掉，返回统一形状的校准概率。

v1.2.0 解决了「怎么起服务、怎么发第一个请求」。但真有多个问题要问的时候，麻烦才出现：

- `/v1/decide` **一次只能问一题** —— 4 个问题要发 4 次请求，还要自己合并结果
- `/v1/systemone` 一次问多题，但 body 形状完全不同（`questions` 字典 vs `kind/state/question`）
- 端口从 3000 到 30002 各不相同
- Laya 多语言版根本没服务，是 `pip install` 后进程内调用
- 各模型返回字段名不统一（`noul` / `probability` / `confidence` / `choices` / `answers`）

这一版把这些差异收敛到一个函数。

---

## 🎯 用法：一套参数，两种接口都一样

```bash
osm-deploy ask autotrust-jev-9b \
  --state-file contract.txt \
  --noul "是否包含自动续约条款" \
  --noul "是否约定违约金" \
  --choice "风险等级=低,中,高" \
  --score  "严重程度=无,轻微,中等,严重"
```

输出直接可用：

```
======================================================================
【决策结果】autotrust-jev-9b
======================================================================
模型     : autotrust-jev-9b  (autotrust/JEV-9B)
接口     : /v1/decide  请求 4 次  耗时 1832.4 ms
  noul_0                   [noul]   True  (p=0.931)
  noul_1                   [noul]   False (p=0.884)
  风险等级                 [choice] 中    (p=0.712)
                           分布: 中=0.712  低=0.167  高=0.121
  严重程度                 [score]  期望 2.43  (峰值 3, p=0.382)
                           分布: 3=0.382  2=0.301  1=0.180
```

Python 里同一个入口：

```python
from src.core.decision_client import ask

r = ask("autotrust-jev-9b",
        state=open("contract.txt").read(),
        noul=["是否包含自动续约条款"],
        choice={"风险等级": ["低", "中", "高"]},
        score={"严重程度": ["无", "轻微", "中等", "严重"]})

# 概率可以直接写进业务判断 —— 这是决策模型相对聊天模型的价值
if r["answers"]["noul_0"]["probability"] > 0.9:
    flag_for_review("含自动续约")
```

## 🔀 自动处理三种差异

### 1. 单题接口 vs 多题接口

| 模型 | 接口 | 4 个问题 → 几次请求 |
|---|---|---|
| JEV 系 | `/v1/decide` | **4 次**（自动拆分 + 合并结果） |
| Clef 系 · OpenJEV · XOR · Decider · Strands | `/v1/systemone` | **1 次** |
| THX-01 | `/v1/decide`（body 是 systemone 格式） | 1 次 |

返回里的 `requests_made` 如实给出实际打了几次 —— 不假装一次搞定。

### 2. 端口

从部署配方取，不用记：

| 模型 | 端口 |
|---|---|
| JEV 系 / Laya / Decider / Strands | 8000 |
| OpenJEV | 3000 |
| THX-01 | 8095 |
| Clef 系 | 30000 |
| XOR | 30002 |

### 3. 返回字段

各模型的返回形状不统一，统一归一化成：

```python
{
  "type": "noul" | "choice" | "score",
  "value": True / "中" / 2.43,        # score 给期望值
  "probability": 0.712,                # 该答案的校准概率
  "distribution": {"低": 0.167, ...},  # 完整分布（有就给）
  "peak": "3",                         # score 额外给峰值档位
}
```

解析时做了宽松兼容：

- `noul` 从 `probabilities[1]`（options 是 `["false","true"]`）或 `answers[x].noul` / `.confidence` 取
- `choice` 优先信 `choice_index`（JEV-27B 会明确回），否则 argmax
- `score` 算**期望值** `Σ(档位 × 概率)`，同时给峰值
- 缺答案显式报错（`{"error": "答案缺失"}`），**不静默当 False**

---

## 🛡️ 该报错的地方明确报错

不在这些地方"猜"：

| 场景 | 行为 |
|---|---|
| 传了不存在的模型 | `未知模型 'xxx'。用 osm-deploy list --category decision 看可用的 12 个` |
| 传了聊天模型（如 `qwen3-8b`） | `qwen3-8b 属于 'domestic-general'，不是决策模型` |
| 传了 library 形态（Laya 多语言版） | `是 library 形态（进程内调用，没有 HTTP 服务）`，并指向 `deploy` 里的进程内示例 |
| 模型没有部署配方 | 明确说没有，指向 `references/decision-models.md` |
| 服务没起 | `连不上 http://localhost:8000（...）。服务起来了吗？先跑 osm-deploy deploy <model>` |
| HTTP 报错 | 带上状态码和响应体前 300 字符 |

**不静默降级**是这条线的原则：拿一个聊天模型去"凑"决策结果，比报错更危险。

## 🧪 测试守的是什么（25 个）

| 组 | 守的东西 |
|---|---|
| 问题构造 | 三原语 → 统一 spec；score 缺档位用默认 0-5；空问题/单选项要报错 |
| body 格式 | `/v1/decide` 的 noul **不能**带 `options`；`/v1/systemone` 每题带 `type` + `criteria` |

| 端到端 | mock HTTP，验证多请求合并与渲染输出 |

## ⚠️ 已知限制

1. **没有真实模型实测** —— 25 个测试全部 mock HTTP。本机 6GB 显存跑不了 8.95B 的 JEV-9B，
   所以「归一化逻辑正确」是验过的，「真实服务端字段是否完全匹配」还需要一次真机验证。
   建议在有 ≥24GB 显卡的机器上跑一次 `osm-deploy ask autotrust-jev-9b`。
2. **library 形态未支持调用** —— Laya 多语言版只报错并指路，没有做进程内适配
   （那需要 `import laya`，与本项目的零依赖原则冲突，更适合放在使用方代码里）。
3. **score 期望值依赖档位是数字** —— 档位是「无/轻微/严重」这类文字时，`value` 退化为峰值档位。
4. **`/v1/systemone` 的 `criteria` 形状各模型略有差异** —— choice 用列表，
   有些模型可能期望 `{标签: 说明}` 的字典。若某模型不认，用 `--json` 看原始返回再调。
