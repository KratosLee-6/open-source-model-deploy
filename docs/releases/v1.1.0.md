## 🆕 模型库 135 → 137（+2）

### 1. EmbeddingGemma 2（Google DeepMind，2026-10-06）

补齐了**多模态检索**这块拼图：文本（含代码）、图像、视频、音频进**同一个 768 维空间**。

| 维度 | 数值 |
| --- | --- |
| 总参 | 740M（HF `safetensors.total` 实测 **744,371,512**） |
| 结构 | 270M 文本骨干（130M transformer + 140M embedder）+ 170M 视觉 + 300M 音频编码器 |
| 输出维度 | 768；**MRL 可截断 512 / 256 / 128** |
| 上下文 | 8,192 tokens |
| 语言 | 100+ 语言；代码任务较一代 **+14%**（MTEB code 68.76 → 78.68） |
| 许可 | Apache-2.0 |
| 本机实测显存 | Q4_K_M **0.5 GB** · BF16 **1.8 GB** |

**两个容易被忽略的工程点**：

1. **纯文本场景只吃 270M**——视觉（170M）和音频（300M）编码器是按需加载的，
   所以标称 740M 的模型在纯检索场景占用远小于参数直觉。
2. **MRL 截断到 256 维几乎不掉点**（MTEB 多语 61.36 → 60.41），
   向量库存储直接省 3 倍；128 维才建议只用文本场景。

### 2. Strands Decider 2B（AWS Strands Labs，2026-10-01）

**System One 决策模型**：不生成文本，输入状态 + 类型化问题，一次前向返回
`noul`（是/否概率）/ `choice` / `score`，每个答案自带校准置信度。

| 维度 | 数值 |
| --- | --- |
| 规模 | 1.9B（`Qwen/Qwen3.5-2B-Base` + LoRA + 读出头） |
| 延迟 | RTX 3090 中位 **115 ms**，可 CPU / Apple Silicon |
| 许可 | Apache-2.0（训练数据与脚本一并公开） |
| 本机实测显存 | Q4_K_M **1.4 GB** · BF16 **4.6 GB** |

> ⚠️ **入库时踩到的坑**：这个 HF 仓库的 `safetensors.total` 返回 `None`，
> 因为它是 **LoRA adapter** 而不是完整权重。工具的 `size_b` 取人工核对的 1.9B，
> **而不是拿一个看起来漂亮的假数字充数**——README 的实测段落如实写了
> 「工具显示 None」这件事。

## 🔌 顺手做了一次「闭源模型该不该进模型库」的鉴别

Jev（TypeSafe AI，2026-09-15 发布）是 System One 类别的开创者，
社区热度极高（发布后一周新增 1,865 个 GitHub 仓库 / 43,750 star）。
但它 **权重未公开、API-only**。

`KNOWN_MODELS` 的语义是「可本地部署的开源权重模型」，每条记录都要能
拉 HF 元数据、算显存、生成启动脚本。Jev 三条全不满足：

| 判据 | Jev 的实际情况 | 结果 |
| --- | --- | --- |
| 有开源权重（HF repo） | 无，官方从未发布 | ❌ |
| 可算显存 / 本地推理 | 无权重 ⇒ 无从计算 | ❌ |
| 可生成部署脚本 | 只能生成 API 调用代码 | ❌ |

**决定：不进 `KNOWN_MODELS`。**

把它塞进去，`list` 和 `detect` 就会说谎——用户会以为它像 Qwen3 一样能下载下来跑，
买完硬件才发现只有 API。这和 v1.0.3 修掉的 MoE 显存误判是**同一类错误**：
让用户按错误信息做决策。

**处理方式**：

- Jev 记录在 [`references/jev-integration.md`](../../references/jev-integration.md)：
  定价（输入 $0.042/MTok、输出免费）、延迟（70–500 ms）、三种原语、
  env 模板、成本测算、设备适配
- 模型库里放**能真跑**的开源对应物 → **Strands Decider 2B**（本次入库）
- 文档里同时列出其他开源替代（Open-Jev、OneJev、sokudan、this-that-model）

> 结论一句话：**闭源 ≠ 不能推荐，但不能混进「可部署清单」。**

## 🔧 修掉三处「会让截图/输出说谎」的实现

这一版的 bug 都在**验证工具自己**身上——不修掉，后面所有实测截图都不可信。

### 1. 截图脚本硬编码编造 nvidia-smi

`regen_screenshots.py` 原先在 `nvidia-smi` 不存在时，会用一段**硬编码文本**顶替：

```python
nsmi = ("GPU  0  NVIDIA GeForce GTX 1660 Ti   WDDM\n"
        "Driver Version: 595.97   CUDA Version: 13.2\n")
```

也就是在一台没有 NVIDIA 显卡的机器上，生成一张「GTX 1660 Ti 当前状态」的截图
放进 README。**这跟数据说错是同一性质的问题，只是更难被发现。**

**修正**：改为如实读本机 GPU；没有 N 卡就写「本机无 NVIDIA GPU」并列出真实显卡信息。

### 2. 截图脚本调到了「别的环境里安装的旧版」

`shutil.which("osm-deploy")` 命中的是 PATH 上**任意一个** osm-deploy。
实测本机 Hermes venv 里装着一个旧版 1.0.0，于是脚本画出的是旧代码的输出——
文件躺在当前仓库里，内容却不是这份源码。等于**用真截图为错误内容背书**。

**修正**：仓库内运行时一律走 `python -m src.cli`（源码优先），
只有在不在仓库根时才退回 PATH 上的 osm-deploy。

### 3. 一次超时让整批截图失败

`run()` 没有捕获 `subprocess.TimeoutExpired`。网络受限时首次拉 HF 元数据变慢，
脚本直接抛异常终止，后面的截图**一张都生成不出来**。

**修正**：超时改为捕获并返回已抓到的部分输出 + 打 warning，
宁可单张图少几行，不让整批失败。

## 🩺 新增：README 事实校验扩到「截图不能是空图」

`scripts/check_readme_facts.py` 增加两项：

- **v1.1.0 新模型必须在库且 README 有介绍**（防止加了代码忘了改文档）
- **每张被引用的截图高度必须 ≥ 120px**——实测截图矮于这个值基本只剩标题行，
  意味着命令没抓到输出。上面第 2、3 个 bug 的症状正是「1400×70 的空图」，
  现在这种图会直接把 CI 打红

同时把「可部署数必须小于总数」写成断言，堵住「137/137 全能跑」这类谎报。
