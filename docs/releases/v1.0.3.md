# v1.0.3 (2026-10-03)

> 显存需求结构化 · 修正一个会导致**错误采购建议**的 MoE 显存误判 · 模型库 127 → 135

这一版的重点不是"多了几个模型"，而是**修掉了一类会让用户按错误信息买硬件的 bug**。

---

## 🔴 最重要：MoE 显存按激活参数算（会导致错误采购建议）

v1.0.2 的推荐逻辑对 MoE 走 `activated_b * 0.6` 算显存。但**MoE 的 expert 权重
全部常驻显存，稀疏激活只降低计算量（FLOPs），不降低权重占用**。

实测影响（24GB RTX 4090 场景）：

| 模型 | 总参 / 激活 | v1.0.2 算出 | 24GB 卡判定 | 实际 Q4 需求 |
| --- | --- | ---: | --- | ---: |
| Kimi-K2 | 1000B / 32B | 23.0 GB | `tight` → **建议能跑** | **720 GB** |
| Qwen3-235B-A22B | 235B / 22B | 15.8 GB | `fits` → **建议能跑** | **169 GB** |
| GLM-4.5 | 355B / 32B | 23.0 GB | `tight` → **建议能跑** | **256 GB** |

也就是准备花两三千块买二手显卡的用户，会被明确告知"这台机器能跑 Kimi-K2"。
实际上要 8×H200 起步。

**修正**：显存按 `size_b`（总参）计算，`activated_b` 只用于计算量与 KV cache 估算。
修正后 Kimi-K2 的 Q4 需求从 23GB 变成 720GB，差距 **31 倍**。

激活比越低错得越狠，而 MoE 恰好是激活比最低的一类（3%~9%）——这不是巧合。

**完整复盘见 [`docs/moe-vram-pitfall.md`](docs/moe-vram-pitfall.md)**

## 🟠 第二个同类错误：自动抓取把激活参当总参

`auto_fetch_models.py` 的 `guess_size_b()` 纯靠正则从模型名抠数字：

| 模型名 | 正则结果 | 真实总参 | 后果 |
| --- | ---: | ---: | --- |
| `MiMo-V2.6-Pro-RL` | `0` | 1024.2B | 数据全丢 |
| `GLM-5.3` | `0` | 753.3B | 数据全丢 |
| `Kimi-K3` | `0` | 2779.9B | 数据全丢 |
| `Llama-4-Scout-17B-16E` | `17` | 108.6B | **把激活参当总参，低估 6.4×** |

`Llama-4-Scout-17B-16E` 里的 `17B` 是**激活**参，`16E` 是专家数，总参 108.6B。
正则只认得 17B，于是让用户以为 16GB 卡能跑 Llama 4 Scout（实际 Q4 需 78GB）。
**和第一个 bug 同一个根因、方向相反。**

**修正**：`size_b` 改从 HF API `safetensors.total` 取（权重元素数 = 真实总参）；
`activated_b` 只认 Qwen 系的明确形态 `<总参>B-A<激活>B`，Meta 系的
`<激活>B-<专家>E` 刻意不猜（宁可留空报警也不填一个看起来合理的错值）。

## 🧮 新增：结构化显存需求（对外接口全面可用）

新增 `src/core/vram_requirements.py`，把散落的显存计算收敛成单一可序列化来源：

- 6 档量化（Q4_K_M / Q5_K_M / Q6_K / Q8_0 / FP8 / BF16）的每参数字节数
- 多卡均分（`gpu_count`）+ context 长度对 KV cache 的影响
- 官方 `vram_min` 优先于启发式（DeepSeek-V4.1-Flash 614GB、Qwen3.5-397B-A17B 400GB）
- `fits` / `tight` / `no` / `unknown` 可行性判定
- `suggest_gpu_plan()` 反推"该买什么卡 / 要几张卡"

**接口暴露**（此前只有 `assess_model` 带着，第三方要拿"我这卡能跑什么"得逐个调）：

| 接口 | 新增能力 |
|---|---|
| `list_models` | `max_vram_gb` 直接筛出放得下的，按显存升序；每条附 `vram_gb_by_quant` + `min_vram` + `is_moe` + `status` |
| `detect_hardware` | `total_vram_gb` / `runnable_count` / `excluded_retired`；推荐条目带 `fit` |
| HTTP `/list` | 同步支持上述 query 参数 |
| MCP schema | 补齐参数定义与模型数说明 |

实测：24GB 卡筛出 104 个、16GB 86 个、12GB 83 个、8GB 77 个。

**知识库导出**：`data/models-knowledge.json`（135 个模型 × 6 档量化的稳定契约，
供第三方工具消费）+ `references/vram-requirements.md`（自动生成的可读对照表）。
两者已接进每周的 GitHub Actions，不会和代码脱节。

## 🩺 新增：模型数据体检（CI 卡口）

这类错误会从任何入口溜进来——手工录入、自动抓取、甚至模型改名。所以把判据固化成了
`src/core/model_lint.py` + `scripts/lint_models.py`，并作为
`refresh-models.yml` 的**第一个业务 step** 执行（ERROR 直接让 job 失败）。

| 判据 | 级别 | 拦什么 |
|---|---|---|
| `missing_size_b` | ERROR | size_b 缺失或为 0，显存算不出来 |
| `size_taken_from_activated` | ERROR | `<激活>B-<专家>E` 形态下把激活参当总参 |
| `name_size_mismatch` | ERROR | 模型名声明的总参与 size_b 不符 |
| `activated_ge_size` | ERROR | 激活参 ≥ 总参（填反了） |
| `moe_without_activated_b` | WARN | 标称 MoE 却没记激活参 |
| `expert_moe_activated_unknown` | WARN | `<激活>B-<专家>E` 是 MoE 但激活参未知 |
| `retired_without_supersede` | ERROR | 标记退役却没指向继任者 |

`auto_fetch_models.py --mode=patch` 在输出前会先过这道闸门，ERROR 候选直接拦下列出原因。

## 📦 模型库 127 → 135（+9，另有 1 个退役标注）

新增模型的 `size_b` **全部取自 HuggingFace `safetensors.total` 实测值**，不是估值：

| 模型 | 总参 / 激活 | 协议 | Q4 显存 |
| --- | --- | --- | ---: |
| **mimo-v2.6-pro**（小米，开源权重第一） | 1024.2B / 42B | MIT | 737.4 GB |
| **mimo-v2.6-flash** | 310.8B / 15B | MIT | 223.8 GB |
| **mimo-v2.6-distill-qwen-9b** ⭐ | 9.41B 密集 | MIT | **6.8 GB** |
| **glm-5.3** | 753.3B / 39B | 自定义 | 542.4 GB |
| **glm-5.3-flash** | 321.3B / 14B | MIT | 223.8 GB |
| **kimi-k3** | 2779.9B / 119B | 自定义 | 2001.5 GB |
| **llama-4-scout-17b** | 108.6B / 17B | gated | 78.2 GB |
| **llama-4-maverick-17b** | 401.6B / 17B | gated | 289.2 GB |
| **qwen3-coder-480b** | 480.2B / 35B | Apache-2.0 | 345.7 GB |

> `activated_b` 的来源已在每条 `note` 里区分：MiMo 的 42/15 是官方公布；
> Llama-4 的 17、Qwen3-Coder 的 35 来自模型名；GLM-5.3 的 39、GLM-5.3-Flash 的 14、

## 🔧 出 v1.0.3 截图时顺手修的 4 个 bug

这版截图是脚本在本机真实运行生成的，一跑就暴露出 4 个此前没人发现的问题：

1. **`wmic` 已被 Win11 24H2+ 移除** → `detect` 一直显示 `内存: 0GB`（实际 15.9GB）。
   改用 ctypes `GlobalMemoryStatusEx`，零外部命令。
2. **「可部署数」用的是全库条数** → 6GB 显卡宣称「总共 136 个模型可在本机部署」。
   现在是 `可部署 83 / 135 个在架模型（其中 11 个仅 CPU 慢速）`。
   这和 MoE 误判是同一类错误：让用户以为自己的机器能跑它根本跑不动的模型。
3. **截图脚本在中文 Windows 上直接崩**（GBK 解码不了 UTF-8 输出），
   所以从 v1.0.2 之后一直没成功跑过。
4. **截图中文全是豆腐块**（首选 Consolas，没有 CJK 字形），且标题里的
   模型数 / 版本号是硬编码的。已改为优先微软雅黑 + 从代码现取。
