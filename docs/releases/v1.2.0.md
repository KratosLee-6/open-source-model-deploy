# v1.2.0 (2026-10-29)

> 决策模型不再是「列得出来但部署不了」—— 12 个 System One 模型逐个核对真实配方，
> `deploy` 从「给一条启动命令」变成「给接口 + 能跑通的真实请求」。

v1.1.1 把 12 个决策模型加进了库、单列了第 9 类，但 `deploy` 对它们仍套用聊天模型的模板：

```
$ osm-deploy deploy autotrust-jev-9b      # v1.1.1
[运行]
vllm serve autotrust/JEV-9B --host 0.0.0.0 --port 8000
```

这条命令**起不出可用的决策服务**：

1. 少了 `--enable-lora --lora-modules jev-decision=<repo>/adapter_vllm` → 起的是纯 Qwen3.5-9B，没有决策头
2. 接口是 `/v1/chat/completions`，而决策模型要 `/v1/decide`
3. 用户起完服务后不知道该问什么 —— 得去读 12 个模型各自的 model card

这一版补的就是这段「最后一公里」。

## 🔧 `deploy` 对决策模型的输出变了

```
$ osm-deploy deploy autotrust-jev-9b      # v1.2.0
[接口]  /v1/decide   →  http://localhost:8000/v1/decide

[运行]
hf download autotrust/JEV-9B --local-dir JEV-9B   # ~18 GB
vllm serve JEV-9B \
    --served-model-name autotrust/JEV-9B \
    --enable-lora --max-lora-rank 32 \
    --lora-modules jev-decision=JEV-9B/adapter_vllm \
    --logprobs-mode processed_logprobs \
    --max-model-len 4096

[健康检查]
curl -s http://localhost:8000/v1/models

[真实请求 · curl]
curl -s http://localhost:8000/v1/decide \
  -H 'Content-Type: application/json' \
  -d '{"kind": "choice", "state": "...", "question": "...", "options": [...]}'

[真实请求 · Python]
import requests
r = requests.post('http://localhost:8000/v1/decide', json={...}).json()
print(dict(zip(r['options'], r['probabilities'])))
```

六段：**接口 → 安装 → 运行 → 健康检查 → 真实请求(curl) → 真实请求(Python)**。

## 📋 12 个模型的真实形态（逐个核对 model card）

### 三种部署形态

| 形态 | 含义 | 模型 |
|---|---|---|
| **service** | 起 REST 服务 | JEV-9B / 27B / 35B · Clef 27B · Clef Flash 9B · OpenJEV 27B · XOR 35B |
| **library** | pip 装完 import 就用，**没有服务** | Laya 多语言 0.3B |
| **hybrid** | 两种都有 | Laya 0.4B · THX-01 · Decider 2B · Strands Decider 2B |

### 端口不统一（这是真实情况）

| 模型 | 接口 | 端口 |
|---|---|---|
| JEV 系 | `/v1/decide` | 8000 |
| Clef 系 | `/v1/systemone` | **30000** |
| OpenJEV | `/v1/systemone` | **3000** |
| XOR 35B | `/v1/systemone` | **30002** |
| THX-01 | `/v1/decide`¹ | **8095** |
| Laya / Decider 2B / Strands | `/v1/systemone` | 8000 |

¹ THX-01 路径是 `/v1/decide`，但 body 用 `systemone` 的多题格式 —— 见下。

## 🐛 两个由测试抓出来的真 bug

### 1. THX-01：路径和 body 格式是两件事

我最初的模型是「路径决定 body 形状」—— `/v1/decide` 就是单题，`/v1/systemone` 就是多题。
THX-01 打破了这个假设。官方 model card 原文：

> `POST /v1/decide` (alias `POST /v1/systemone`, TypeSafe-compatible) takes
> `{"state": ..., "questions": {...}}` and returns `{"answers": {...}, "latency_ms": ...}`

**路径叫 `/v1/decide`，body 却是 systemone 的多题格式。**

修法：`decision_recipes.py` 里用两个独立字段 —— `endpoint`（URL 路径）和
`body_format`（body 形状）。测试 `test_thx01_path_and_body_format_differ` 专门锁住这一点。

### 2. 「不能用 vllm serve」这句话本身会让测试失败

`test_deploy_unknown_decision_model_is_honest` 断言未核实模型的 `run_cmd` 里不能出现
`vllm serve`（防止有人误复制）。我原本的提示文案里写了「不能用 vllm serve 通用模板部署」
—— 里面就有这个词，测试直接红。

改成「不能用通用 chat 模板部署」，既准确（问题在模板不在 vllm，Clef 还用 SGLang）又不触发误判。

> 这类「测试比人更较真」的情况，说明测试写对了 —— 它守的是「别让用户复制到错命令」，
> 而不是字面匹配。

## 🧪 测试守的是什么

新增 42 个测试，分四组：

1. **覆盖率** — `KNOWN_MODELS` 里每个 `decision` 模型都必须有配方（不许出现「列得出来但部署不了」的洞）
2. **字段完整性** — form / endpoint / body_format / install / run 缺一不可；library 形态不能有 port
3. **核心回归** — decision 类**不能套 chat 模板**：`run_cmd` 里出现裸 `vllm serve` 就必须同时带 adapter/shim
4. **不影响老模型** — 非 decision 模型的行为完全不变

## ⚠️ 已知限制

1. **OpenJEV 27B 是 CC BY-NC 4.0（非商用）** —— 商用前必须换模型或单独授权。
2. **Strands Decider 的 HF 仓库只有 91.5MB LoRA adapter** —— 必须另配 `Qwen/Qwen3.5-2B-Base`。
3. **OpenJEV 需要两步启动**（vLLM :8000 → shim :3000）—— 只起 vLLM 拿不到 `/v1/systemone`。
4. **本版只做「怎么起 + 怎么问」**，还没做统一客户端（`decision_ask()` 抹平 12 个模型的接口差异）
   —— 那是 v1.2.1 / W1b 的范围。
5. 配方来自各模型 model card（2026-10-29 核对）。**上游改命令时这里会过期** ——
   重跑 `scripts/verify_decision_endpoints.py` 复查。
